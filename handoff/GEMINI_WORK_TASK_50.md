## Одна большая задача, 10 внутренних партий по пять
Пройди **все 50 вопросов**, строго в порядке `manifest.ids`. Не останавливайся после пятой, десятой или тридцатой записи. Для экономии контекста зафиксируй промежуточный результат каждой пятёрки в отдельном файле, затем объедини в финальный отчёт. Если не хватает ресурса завершить 50 — обозначь действительно выполненные и UNREVIEWED, никогда не ставь автоматические PASS оставшимся.

## Регламент для каждого ID — НЕ ПРОПУСКАТЬ
1. Сначала приведи точные `question.text`, все `question.answers` со своими исходными индексами (в разных билетах вариантов может быть 4 или 5) и `question.correct`. Самостоятельно проверь ключ и возможный второй верный вариант при данных оговорках. Если задача двусмысленна, статус FIX.
2. Разбери **каждый вариант отдельно**, включая ВСЕ дистракторы (их число зависит от конкретного вопроса): техническая причина его верности/ложности именно в этом условии. Не объединяй ответы фразой «остальные неверны».
3. Проверь `explanation.brief`, `explanation.plain`, `explanation.professional`: персонализацию, терминологию, контекст, полноту, техническую точность и отсутствие шаблонных заглушек.
4. Проверь `explanation.commonTrap`, `explanation.practicalTip`, `explanation.practiceLink`: практический совет должен соответствовать конкретному вопросу и реальной диагностике, а не общим спискам `ss -tulpn` или «линк → маршруты → DNS». Любой generic/paste вне контекста — FIX.
5. Проверь точное соответствие `lesson.id#lesson.anchorId` и две **фактические** секции `lesson.sections.plain` и `lesson.sections.professional`. Проверь `lesson.coverageIssues`. Если непусто — запрещён PASS. Ссылка сама по себе НЕ доказывает браузерную навигацию.
6. При спорном RFC, таймере, поле протокола, варианте поведения оборудования можно обращаться к первичным RFC/стандартам. Источник указывай ссылкой с номером раздела; не выдавай по памяти цитату за проверенную.
7. Статус каждого ID: PASS (всё подтверждено фактически), FIX (укажи точный дефект и минимальную правку), REVIEW (материал/доказательство недостаточно). Никакого «PASS всем» без отдельной технической аргументации.
8. Не правь хорошие уроки ради красивого стиля; укажи узкую исправленную фразу и поле исходного JSON. Отмечай ошибки ключа отдельно от ошибки совета/стиля/урока.

## Обязательные выходные файлы
**A. `verdicts.json`** — ровно 50 объектов в порядке `manifest.ids`, каждый с `id`, `sourceSHA`, `status`, `correctKeyReview`, `alternativesReview` (РОВНО по одному объекту `{index,text,verdict,evidence}` на КАЖДЫЙ исходный вариант ответа; нельзя ограничивать четырьмя, если есть пятый), `briefReview`, `plainReview`, `professionalReview`, `commonTrapReview`, `practicalTipReview`, `practiceLinkReview`, `lessonId`, `anchorId`, `lessonPlainReview`, `lessonProfessionalReview`, `coverageIssues`, `factualIssues`, `proposedChanges`, `externalSources`, `verificationLimits`, `confidence`. Проверяемость важнее лаконичности.
**B. `REPORT.md`** — сводная таблица 50/50 по ID со статусами PASS/FIX/REVIEW, количество каждого статуса, затем предметные проблемы, предложения минимальных исправлений и слабые места методики.
**C. `FIX_PROPOSALS.md`** — только конкретные найденные дефекты, с ID, точным полем, `Было → Стало` и основанием; если FIX нет, явно написать, что не найдено.
**D. По возможности ZIP** со всеми тремя файлами. Можно дополнительно делать промежуточные файлы `partials/part01.json` ... `part10.json`, но итоговые `verdicts.json` и `REPORT.md` должны охватывать **все 50**.
