# Химик: Kimi Agent через GitHub Issue

Базовая инфраструктура merged в #359. Исправление publisher подготовлено в
`fix/kimi-pr-publication`; до его приёмки оно не меняет опубликованный worker.
Для автоматического Draft PR владелец должен включить **Settings → Actions → General →
Workflow permissions → Allow GitHub Actions to create and approve pull requests**.
Иначе GitHub возвращает 403 `actions_pr_creation_disabled`, даже при job permission
`pull-requests: write`. Не добавлять PAT и не повторять модель ради исправления этого отказа. Не создавать `[KIMI]` Issue
для проверки до разрешения платного запуска. После merge workflow в main запуск
происходит только по **созданию** Issue от `apotet`, sender/actor также `apotet` User.
Пример **тела** Issue с заголовком `[KIMI] Аудит PoE` (JSON без Markdown fences):

```json
{
  "mode": "audit-only",
  "model": "kimi-k3.1-pro",
  "task": "Проведи инженерный и педагогический аудит урока. Укажи цитаты, приоритеты и ограничения проверки.",
  "target_files": ["src/data/lessons/l1-poe-budget.ts"],
  "verification": "structure",
  "max_tokens": 8192
}
```

Обязательны `task` и `target_files`; прочие поля имеют значения по умолчанию из
примера. Неизвестные и дублирующиеся ключи отклоняются. Модель закреплена:
`kimi-k3.1-pro`, reasoning high, streaming с usage, без tools/fallback/reconnect.
Секрет — существующий `MOONSHOT_API_KEY`, только в шаге единственного платного запроса.
Тело Issue не попадает в shell или expressions workflow.

## Вход и лимиты

- `mode`: `audit-only` или `edit`.
- `task`: 1–12000 символов, обычный текст, без файлов/команд, исполняемых агентом.
- `target_files`: 1–4 уникальных существующих файла строго `src/data/lessons/<name>.ts`.
  Traversal, абсолютные пути, shell-конструкции, symlink-файлы/родители и файлы
  инфраструктуры реестра запрещены. Новые файлы не создаются.
- `verification`: `structure` (всегда AST + typecheck); `poe-full` дополнительно
  запускает существующую регрессию инжекторов/сплиттеров и требует ровно этот урок.
  Ослабляющего профиля `tsc` у Issue-адаптера нет.
- `max_tokens`: целое 1024–8192, общий бюджет reasoning + ответа.
- Полные messages — максимум **39000 UTF-8 байт**, плюс 2048 токенов резерва framing.
  Все целевые файлы передаются целиком, без усечения. Большой пакет отклоняется.
- Жёсткий финансовый потолок **$0.25 на Issue**. Верхняя предварительная оценка:
  `((message_bytes + 2048) × 4 + max_tokens × 10) / 1000000`.
  При максимальных настройках — **$0.246112**, ниже $0.25.
  Байты консервативно ограничивают токены; скидка кеша не предполагается.

Тарифы проверены **25.11.2026** по [платформе Kimi](https://platform.kimi.ai/),
[Model Pricing](https://platform.kimi.ai/docs/pricing/chat) и
[Context Caching](https://platform.kimi.ai/docs/guide/context-caching): input $2,
cache hit $0.20, cache write 5m $2 / 1h $4, output $10 за 1M токенов, до налогов.
Input разбит на взаимно исключающие miss/read/write, это не суммирование всех
трёх тарифов на одни токены. В предварительной оценке намеренно используется $4
на весь input: без экономии кеша, с запасом на запись 1h у ранее закреплённого
кеш-префикса. Окно K3.1 Pro — 1M токенов; выбранные лимиты существенно ниже.
Тарифы следует перепроверять при изменении цен; предел $0.25 из Issue не меняется.

`accounting.json` сохраняет число попыток, предварительный максимум, raw usage,
верхнюю стоимость по usage и `cost_usd`. Последняя вычисляется только при валидных
input/output, cache read/write и детализации TTL из разрешённых числовых billing
headers (при нулевой записи headers не нужны). При отсутствии `cached_tokens`
**всегда** сохраняется `cost_usd=null` и выводится `cost_range_usd.min/max` —
расчётный диапазон до налогов, а не точное списание. Неизвестный cache read не
считается нулём. При неизвестном write/TTL диапазон расширяется; противоречивые
счётчики не дают неподтверждённую точную сумму. Для #360 (input 5349, output 4076,
5m write 5120, 1h write 0, read не указан) это $0.0510458–$0.051458.
`usage_cost_upper_bound_usd` остаётся отдельной общей консервативной границей. Headers целиком не сохраняются.
При timeout стоимость неизвестна, попытка остаётся потраченной, повтор запрещён.
Это лимит на задание, не общий бюджет аккаунта.

## Claim и результат

После валидации, бюджетного preflight, baseline typecheck и проверки поддержки
структуры исходного edit-файла создаётся durable comment
`<!-- kimi-agent:claimed:v1 -->`. Перед POST просматриваются **все страницы** комментариев.
Наличие маркера блокирует задание. Не удалять claim-комментарии.
Один curl HTTP POST: отключён curlrc, `--retry 0`, redirects не разрешены,
общий timeout 600 секунд, ограничение размера ответа 2MB. Секреты не печатаются,
ключ редактируется в SSE перед выгрузкой. Никаких автоматических повторов.

`issues: opened` — единственное событие. Comments, edited, reopened и rerun не запускают
платный запрос; paid worker/claim/run запрещают `run_attempt != 1` и неавторизованные события.
Один Issue сериализуется concurrency group. Локальный счётчик попыток записывается
**до** HTTP POST и также блокирует второй вызов.

В Issue публикуются статус, отчёт/CHANGES (длинный текст — с явной пометкой отрывка),
usage/стоимость, Draft PR и ссылки на run/artifact. Полные данные — в артефактах 30 дней.
Если проверки edit не прошли, это отказ, не успех, даже когда API вернул ответ.
Если prepare не прошёл, комментарий содержит отсутствие отчёта и api_calls=0;
тип сбоя и входные данные доступны в диагностическом артефакте.
Нельзя создавать Issue-дубликат или делать rerun после неопределённого списания без
отдельного решения владельца. Нет автоматического Telegram: запрос требует комментарий Issue.

## Режим edit

Задать `"mode": "edit"`. Это редактура **текстовых литералов** (body, summary, title,
label, explanation, question, prompt, hint, text, description). Issue-адаптер не
разрешает менять исполняемый код, imports, ID, структуру и выражения; для расширения
структурных разрешений нужен отдельный обзор инфраструктуры. Ручной Kimi Agent
сохраняет прежние возможности и остаётся без изменений.

Переиспользованы `build_payload.py`, `parse_sse.py`, `extract_candidates.py` и
`structure_check.mjs`. До применения дополнительно сравнивается полный AST файла
в `kimi_issue_text_guard.mjs`: отличаться могут только разрешённые строки. Это
защищает в том числе код вне объекта урока и подстановки `${...}`. После извлечения
идут diff, AST, typecheck и выбранная регрессия. Оригиналы/кандидаты исключаются из
tsc glob на время компиляции; команд из ответа модели нет.

Ветка и Draft PR публикуются только после всех ворот отдельным job из чистого
checkout SHA события. Платный job не имеет `contents:write` или `pull-requests:write`;
ключ провайдера не передаётся компилятору/тестам. Publisher сверяет SHA/хеши,
повторяет AST-проверки, проверяет неподвижность main и создаёт через GitHub Git API
только целевые blobs/tree/commit и **новую** ветку
`kimi/agent-run-issue-<issue>-<run_id>`. Ранее существующая ветка не перезаписывается. Она может быть повторно использована
только после сверки direct parent, списка путей, blob-хешей и режима файлов с
проверенными кандидатами. Существующий OPEN/Draft PR должен точно совпадать с
repo/head SHA/base; иначе отказ. Publisher не переводит #361 или другие PR в Ready.
Checkpoint публикации сохраняется до POST /pulls. Только metadata-публикация и
комментарий допускают восстановление; это не разрешение повторять paid worker.
PR всегда Draft, base main; merge/deploy агент не выполняет. Если main успел
измениться, публикация отклоняется без нового вызова модели.

## Офлайн-проверка и ручной запуск

Новый набор: `python3 tests/test_kimi_issue.py` (нужен TypeScript 5.9.3, как в CI:
`npm install --prefix tests/vendor --no-save --ignore-scripts typescript@5.9.3`).
Он мокает GitHub и curl, запускает настоящие shared SSE/extraction/AST инструменты.
Проверки typecheck и GitHub publication в тестах адаптера моканы; это проверяет
ворота и ветвление, не изображает живой платный запуск. Baseline проекта отдельно
проверяется локальным `npm run lint` и Fast PR gate.

Существующие 25 offline + 17 agent-tools и security-тесты сохранены; новый набор
подключён к `kimi-agent-tests.yml` для PR. Файл `kimi-agent.yml` и его
`workflow_dispatch` не изменены. ZAI workflow/скрипты/лимиты не изменены.
