# Learning quality operations

`npm run quality:scan` imports the **real runtime** bank, deep-dive resolver, lesson resolver, glossary, tooltip matcher, practice destinations and CLI scenarios. It inventories every ID in `docs/audits/learning-coverage-latest.{json,md}`. Output is deterministic (no timestamps). The JSON is the unified backlog, including raw text paths/context, structural failures, review candidates, content/dependency fingerprints and independent review status. Historical audits remain historical evidence with their original limited scope; they do not grant semantic PASS.

`npm run quality:gate -- --base COMMIT` compares both runtime banks, including deletions. Invalid/unavailable base fails closed. New/directly changed content requires its complete structural pack and independent whole-material review. Unchanged legacy gaps do not block unrelated UI/CLI changes. New structural regressions in unchanged materials do block. Glossary/lesson dependency edits invalidate prior semantic receipts without demanding repair of all old dependent material in one PR. This does not prove lesson relevance or prose correctness automatically.

## Independent review without asking the owner to test hundreds of IDs

1. Select a small logical batch of REVIEW IDs from the registry. Run `npm run quality:packet -- question:ID` (also lesson/glossary/practice) to export **full current material**, dependencies, answer key, explanation layers, candidates and hashes. A reviewer different from the author reads each complete packet. Use official technical references cited by the material; ambiguous claims remain REVIEW or FIX.
2. Check technical correctness, beginner comprehension, key consistency, lesson relevance and terminology in context. Check both plain/pro; inspect headings, tags, raw abbreviations and English technical words, not just marked markup. Where practice exists verify that it teaches the actual skill. No practice may be the correct contextual decision; it is not automatically a defect.
3. Record evidence and every candidate disposition (`token`, exact `path`, `decision`, `reason`). Allowed resolved decisions: `defined-in-context`, `defined-interactively`, `not-a-learning-term`. A code identifier or citation can be a false positive, but needs a contextual reason, not a blanket all-caps exclusion. A missing useful definition is a FIX; add it, re-scan, re-review affected content. Candidates are **not confirmed errors**.
4. Append a receipt in `reviews.json`: `id`, `materialId`, exact `contentHash`, `dependencyHash`, `candidateDigest`, `author`, different `reviewer`, `scope: whole-material`, `result: PASS`, `evidence: [paths/URLs with rationale]`, `criteria` with `technical`, `beginner`, `answerConsistency`, `lessonRelevance`, `terminology`, and `candidateDecisions` in packet order. Review/FIX or changed-claims evidence is retained separately and never upgrades a whole material to PASS. Do not copy synthetic test receipts into real reviews.
5. Re-run scanner/gate and focused tests/browser cases. Fingerprints reuse completed unchanged work; edits to material or dependencies invalidate it. The owner does not have to perform mass review. Review evidence is auditable repository metadata, **not cryptographic proof of reviewer identity**. Repository reviewers must verify its provenance.

No whole-material receipts are currently claimed. `docs/audits/issue-233-independent-review.json` records an actually executed scoped independent review and its explicit limitations. The Wi-Fi pilot remains REVIEW until its whole-material review and candidate dispositions are complete. The gate deliberately rejects that incomplete pilot; do not weaken it to make this PR green.

## Executed checks vs limitations

The scanner validates IDs, answer indices, required layers, generic fallback flags, plain/pro blocks, duplicate levels, actual lesson mappings, exact glossary tags, tooltip metadata, raw candidate discovery, practice keys and actual CLI scenario IDs. It checks URL syntax and recognized internal lesson anchors. It does not claim external server reachability, semantic relevance from token overlap, or browser navigation from a nonempty URL. Existing real-component navigation tests and real-browser suites provide separate evidence. Code samples remain candidates but are not forced into tooltip buttons.

The workflow `Learning quality / Learning content gate` runs on every main PR, without path-filter deadlocks. Its mutation step verifies a deliberately invalid answer produces exit code 1. Tests also cover missing layers, bad destinations, deletion, raw unknown terms, stale/self/partial review and dependency invalidation. This is a failing **status check**, not branch protection by itself. GitHub branch-protection API returned 403 to this integration; required-check configuration cannot be verified or changed. A repository administrator must require this exact check to enforce GitHub merge blocking. Do not call green CI protected merging.

PR #232's standard is included in `docs/LEARNING_CONTENT_STANDARD.md`. No production repository or deployment is part of this work.

`npm run quality:queue -- --kind lesson --limit 10` exports a bounded deterministic batch of full packets for an independent reviewer. Matching, evidence-bearing whole-material FIX/REVIEW receipts prevent repeating an already executed unresolved review; the material stays in the repair backlog, never PASS. A changed fingerprint puts it back in the review queue. Do not fabricate receipts merely to advance the queue.

`npm run quality:links` separately checks **external URLs in source-reference fields**, deduplicating fragments and retaining every originating material ID/path. It records reachable, HTTP 404/410, and UNVERIFIED (timeouts/access denial) in `scripts/.cache/learning-quality/external-links.json`. This checks availability only, not fragment existence or reference relevance. Example URLs in question scenarios are not fetched. CI preserves this evidence, but external availability is not a merge blocker because transient remote failures cannot justify blocking unrelated work.

The issue-171 frozen baseline has an intentional migration of exactly four protected-file hashes: the lesson title renderer, glossary and two Wi-Fi lessons. Question-bank order/content/keys, level audit projection and every other protected hash remain intact. This records source evolution; it is **not** semantic approval of the Wi-Fi pilot.
