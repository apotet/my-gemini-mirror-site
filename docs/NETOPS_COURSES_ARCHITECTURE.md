# NetOps Courses · архитектура и план этапа 1

**28.11.2026 · проект этапа 1, не рабочая функция.** [#558](https://github.com/apotet/my-gemini-mirror-site/issues/558) задаёт продукт, [#559](https://github.com/apotet/my-gemini-mirror-site/issues/559) задаёт инвентаризацию и архитектуру этапа 1. [Инвентаризация двух NetOps и старого сайта](NETOPS_COURSES_INVENTORY.md) закрепляет снимки и текущие маршруты. В этом Draft нет runtime, изменения банка, макетов, workflow, публикации или закупки. L3 продолжает отдельную очередь.

## Решения и открытые вопросы

**Задано владельцем:** учить от простого к сложному через существующие материалы по ID; оглавление, предыдущий/следующий, продолжение после F5; пять уровней; не менее 20 вопросов в итоговой попытке каждого курса с охватом его тем; связанная практика и обратный путь; гостевой доступ ко всему обучению. Визуальный стандарт: короткий первый слой, технические подробности по желанию, статичные SVG/схемы/таблицы у объясняемого шага, мобильная читабельность. Визуальный `tcpip-model` из [#557](https://github.com/apotet/my-gemini-mirror-site/pull/557) вошёл в зеркало после снимка инвентаризации; это не отметка личной приёмки и не обязательный шаблон всех уроков.

**Согласовано владельцем для внутреннего пилота** [в #560](https://github.com/apotet/my-gemini-mirror-site/pull/560#issuecomment-7233872649): только `addressing` на зеркале, гостевой локальный прогресс, **20 вопросов, порог 80% (16 из 20), без таймера и без лимита повторов**. «Изучен» отмечает завершение учебных шагов, «Пройден» — успешный итог; одно не выставляет другое. 20 семейств обеспечивают отсутствие реестровых повторов в одной попытке, а не 20 разных навыков. 40 семейств — цель разнообразия на этапе масштабирования, не условие внутреннего пилота.

**Открыто:** состав остальных курсов, масштабирование и будущая синхронизация. Регистрация только для sync; Google, GitHub и email пока кандидаты; Supabase не выбран. Пилот не включает облако, платные сервисы, production, другие курсы и изменения очереди L3.

## Единый каталог: ссылки, а не копии

Один версионированный справочник курсов над текущими реестрами. Эскиз контракта (имена ещё можно менять):

| Сущность | Что хранить и чем разрешать |
| --- | --- |
| `Course` | `courseId` (стабильный, не заголовок), ревизию каталога, название/краткий результат, `recommendedAfter[]` по course ID, список `stepId`, `assessmentId`. Зависимости — советы, не запреты на открытие. |
| `CourseStep` | Стабильный `stepId` внутри курса, `topicId`, `lessonId` из `LESSONS`, необязательный `sectionId` из резолвера разделов, цель, оценка времени (где можно измерить), ссылки на элементы. Один урок может встречаться в нескольких курсах; прогресс его просмотра и факт завершения курса не одно и то же. |
| `ResourceRef` | Типизированные ссылки: `lesson`, `practice` (существующий ключ/вариант/сценарий), `visual` (ID ресурса + якорь), `cheatsheet` (канонический ID блока или существующая карточка), `question`, `command`, `case`, `term`. Для будущего ресурса только `planned` с текстом без активной кнопки. |
| `AssessmentBlueprint` | `assessmentId`, версия, минимальная длина, тематические квоты, допустимые пять учебных уровней и явно принятый набор question ID на каждую тему. Корректный ответ, варианты, объяснения и фото идут из банка, а не из курса. |
| `CourseProgress` | Пройденные шаги и точка продолжения (`courseId/stepId/sectionId/mode`), версия схемы, локальные записи событий, ссылка на идентификатор итоговой попытки и её снимок. Не хранить в реестре курсов персональные данные. |

Валидатор будущей реализации проверяет существование идентификаторов, уникальность, граф зависимостей без циклов, принадлежность якоря и его наличие в обоих режимах, допустимые practice key/variant, квоты без повторов семейств, и невозможность включить макет либо planned как действующий путь. Не переименовывать существующие ID и привязки. Для переноса шага поддержать явный алиас версии или показать «шаг больше недоступен» и ближайший действующий шаг. Библиотека знаний, индекс поиска и исследовательская карта читают одни и те же реестры. Категории, метки и размеры выбранного курса не переопределяют плашки личной приёмки уроков.

**UX-переход.** В навигацию добавить один вход «Курсы» (десктопное меню, мобильное меню/палитра без шестой нижней иконки на пилоте). Внутри: список курсов, оглавление, карточка «Продолжить», предыдущий/следующий. Старые «Тесты», «Теория», «Практика», IPv4/IPv6 и глубокие ссылки не перемещать. Для новых курсов выбрать воспроизводимый адрес в SPA: например, hash с известными `courseId/stepId` без серверного роутинга Pages; конфликт с существующими якорями проверить до выбора формата. При возвращении через «Назад»/«Вернуться к разделу» хранить источник по ID, режим, положение и конкретный триггер. Внутри сеанса использовать существующие фокус/позицию, после F5 восстанавливать по устойчивому якорю (не по DOM-объекту или старым пикселям). Прямой вход в стенд не придумывает источник возврата. После распознавания контекста применять «Закрепи на практике» для упражнения, «Посмотри наглядно» для схемы, «Поэкспериментируй» для модели с управляемым изменением; ни лаборатория, ни анимация не обязательны по умолчанию.

**Оформление.** Оставить «Простыми словами» и «По делу», точные ссылки, глоссарий, хештеги, фото/источники и текущие плашки. Шпаргалки, рисунки, команды и проверяемые примеры рядом с содержанием; обтекание на широких экранах, вертикально на узких. «Главное», «Типичная ошибка», «На практике», «Шпаргалка», «Проверь себя», «Подробнее» только если помогают цели; краткая самопроверка там, где уместно, не заменяет итог 20. Иллюстрации каждый раз требуют технической проверки, читаемости, alt и проверенной лицензии. Не переписывать одобренные уроки и не тиражировать #557 автоматически.

## Карта курсов и проверка квот итогов /20

Карта предварительная: сначала введение, далее по графу. Допустимый уровень — именно `learningLevel` 1…5 (**Основы, Понимание, Применение, Диагностика, Эксперт**), не `difficulty` урока и не настройки пробного экзамена. В графе проверено отсутствие циклов. «Из числа доступны» означает структурную кандидатуру, а не содержательный PASS или наличие статуса approved. Для будущего `intro` до CLI нужны LAN и WAN, базовые топологии (звезда, кольцо, шина) и модель «клиент запрашивает, сервер отвечает». Сопоставление этих тем с уроками, упражнениями и итогом ещё предстоит; строка таблицы сохраняет прежнюю измеренную ёмкость трёх корзин и не покрывает эти темы.

**Метод.** Для каждого тематического слота использованы только вопросы со статусом `ASSIGNED`, разрешённого уровня и с каноническим уроком указанного блока (`getLessonForQuestion`); для промышленного Modbus дополнительно исключены LDAP/RDP по теме вопроса, а из квоты IPv6 исключён транспортный вопрос `gap-pack3-08` про UDP checksum. Разные варианты с одним `family` считаются одним семейством; без family семейство равно question ID. Квоты проверены максимальным двудольным сопоставлением «слот ↔ семейство», чтобы семейство из двух тем не засчитать дважды. В знаменателе — предложенная квота вопросников по теме, в числителе — число семейств-кандидатов, причём сумма числителей может превышать размер их объединения. Если не набрали 20, не брать вопросы из посторонней темы и не открывать итог. Перед запуском вручную проверить формулировки, варианты, результаты обучения, изображения, разборы и нужные точные связи. Нехватка по темам не устраняется большим суммарным количеством банка. Поле `family` отсеивает повторы по реестру, но разные семейства не равны разным навыкам. Для каждого обязательного навыка потребуется явное соответствие «навык → проверенный вопрос или упражнение».

Ни для одного курса из результата не следует содержательная готовность всех обязательных навыков, утверждённый итог или готовность UI. Вариации /25, /26 и /27 могут проверять один и тот же навык, даже если в реестре это разные семейства.

Примеры семантических пробелов при оценке 20/20: для PoE нынешняя квота уровней 1–2 опирается на вопросы чтения прибора и подключения, а вопросы расчёта общего бюджета из `l1-poe-budget` и вопрос о подключении из `l1-poe-injectors-splitters` относятся к уровню 3 и не входят в подсчёт. Для VLAN есть вопросы о кадре, access/native VLAN и несвязности, но у `cli-vlan-trunk` и `l2-svi` нет ни одного канонически закреплённого вопроса; освоение сквозной настройки и проверки trunk/SVI этими числами не доказано. Это пункты дальнейшей проверки, не разрешение расширять работу сейчас.

### Контрольный набор адресации: 20 ID, без публикации вопросов

Это проверяемый пример набора для staging, не ключ и не фиксированный порядок. Все 20 ID относятся к нужным каноническим урокам и дают 20 разных семейств по реестру. Несколько семейств могут проверять одно действие; охват проверяется отдельно по связям «навык → вопрос или упражнение». В масках из пяти слотов не более одного на прямое преобразование отдельного октета: не брать одновременно 128 и 252 или два направления для одного числа. `gen-bin-dec-252` по фактическому условию проверяет CIDR-префикс полной маски 255.255.252.0, а не перевод одного октета; семантику определять по условию, не по ID.

- **Смысл маски и частные адреса (5):** `l3-12`, `l3-06`, `gen-bin-dec-128`, `gen-bin-dec-252`, `gen-mask-30`.
- **Границы сети, on-link и выделение подсетей (9):** `gen-bc-25-2`, `gen-bc-26-1`, `gen-hosts-27`, `l3-11`, `gen-net-29-0`, `l3-d02`, `new-l3-23`, `gap-pack1-06`, `gen-block-28`.
- **Локальная настройка IPv6 (6):** `review-ndp-1`, `review-ndp-2`, `review-ndp-3`, `review-slaac-4`, `review-slaac-5`, `l3-d06`.

Итог пилота проверяет IPv4-маски и подсети (частные диапазоны, границы, размер, on-link/шлюз, разбиение) и локальную настройку IPv6: link-local, NDP, RA, DAD и SLAAC. Это не полный курс IPv6 или маршрутизации. Запись IPv6 проверять **отдельным практическим упражнением**: в действующем IPv6-тренажёре ввести каноническую форму («Сжать») и полную запись в восьми группах («Развернуть») на двух задачах. Например, `2001:0db8:0000:0000:0000:0000:0000:0042` → `2001:db8::42`; `2001:db8:1234::1` → `2001:0db8:1234:0000:0000:0000:0000:0001`. Упражнение засчитывается только после проверки обоих введённых ответов, отдельно от /20; открытие экрана не считается. На этапе 2 проверить корректный и ошибочный ввод, сохранение отдельного результата и возврат к шагу; сейчас связь курса с упражнением ещё не реализована.

**Итоговые попытки.** Сэмплер нового типа получает закрытый набор курса, выравнивает по квотам, не повторяет вопрос/семейство, не подмешивает другой курс даже при дефиците. Фиксировать точные IDs, порядок вариантов, ключи и снимок отображаемого текста на момент попытки; новое наполнение не переоценивает старые ответы. «Практиковался», «изучен», «пройден», «не осталось доступных вопросов» имеют разные признаки. После завершения показывать результаты по темам, разбор ошибок и ссылку на существующий урок/раздел, если соответствует. Не склеивать с действующим trial, таймером или его фото-квотами; регрессионно доказать сохранение существующих пробных попыток и правил фото. Для физического курса правила фото нового итогового режима обсуждаются отдельно. Ни успешное прохождение обязательной части, ни 80% автоматически не доказывают овладение всеми темами.

## Локальный прогресс, синхронизация и доверие

1. **Сначала guest/local-first.** Новый версионируемый слой курса хранит свои записи отдельно по приложению/окружению (пути Pages не изолируют origin). Не менять `osi_*` и слоты N4/N5 для других режимов. Восстановление после F5, отключённой сети/неполной записи, конфликтов вкладок, отсутствующего ID и заблокированного storage; честно показывать, когда запись не сохранена. На стартовом экране предлагать продолжение, а не маркировать прочитанным после открытия. Local-first не требует регистрации.
2. **Данные — разные сущности.** Завершение шага курса, закладка урока и курсор чтения, снимок итоговой попытки и действия в работе над ошибками хранятся отдельно. У событий стабильный ID, схема и допустимое множество полей; повтор доставки и импорта идемпотентен. Завершённые попытки неизменяемы, активные попытки двух устройств не затирают друг друга: сохранить обе и дать выбрать, какую продолжить. Квитанции связывать с одной попыткой/ответом; не складывать агрегаты двух устройств. Удаление избранного/сброс — отдельное намерение с подтверждением, а не исчезнувшее поле; синхронные конкурирующие завершения шага объединять по ID; курсор выбирается по серверному порядку событий с детерминированной развязкой, не по ненадёжным часам устройства. Гостевая и аккаунтная записи не смешиваются при смене пользователя.
3. **Импорт первого входа.** Только после подтверждения и предварительного просмотра, инвентарь источников локального хранилища включая общее origin, неизвестные/устаревшие данные — отдельный отчёт, исходные ключи не удалять. Сохранить копию/экспорт до миграции, миграции повторяемы, импорт версиями. Возврат истории, согласованный конфликт, офлайн-очередь и повторная доставка тестируются на двух устройствах, в том числе вкладках; логин не делает сервер единственным источником. Вход нужен для синхронизации и не перекрывает гостю материалы.
4. **Поставщик и бюджет только отдельным решением.** Интерфейсы `AuthAdapter` и `ProgressSyncAdapter` с локальной реализацией/контрактным двойником сейчас; потом отдельная сравнительная оценка управляемого Auth+DB (включая названный владельцем Supabase как гипотезу), управляемого Auth + собственного API и self-hosted. Посчитать MAU/устройства, событий в день, размер попыток, месяц чтений/записей/трафика, резерв/восстановление/стоимость исхода; проверить удобство email и OAuth, регионы и доступность с телефона, политику приватности и переносимость. Не фиксировать цену/платёж, поставщика или нулевую стоимость. Экспорт и удаление аккаунта, отзыв устройств и ограничение хранения обязательны при появлении sync. Сервер подтверждает владельца записи, изолирует аккаунты и окружения; RLS обязательна **если** выбран Supabase. Секреты и привилегированные ключи не попадают во frontend; курс/публичные материалы не отправляются как пользовательская аналитика. До отдельного решения нет реальных учётных записей, облачных ресурсов и подключения внешних API.
